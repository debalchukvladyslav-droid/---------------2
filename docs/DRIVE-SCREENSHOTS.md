# Скріншоти без копій у Supabase Storage

Файл залишається у приватній підключеній папці Google Drive. У таблиці
`screenshots` зберігаються ідентифікатор оригіналу, метадані та стабільний шлях
`screenshots/<owner>/drive/<fileId>/reference`. Це запис бази, а не Storage object.

Перегляд проходить через `/api/drive-service?action=screenshot`: JWT і RLS
визначають право перегляду, сервер перевіряє папку Drive і передає оригінал
браузеру. Кеш пристрою зменшує повторні скачування. Публічний доступ до папки
не потрібен; service account має зберігати доступ до підключеної папки.
Передавання оригіналу витрачає трафік Vercel, але не додає файл у Supabase Storage.

## Виправлення 11 листопада 2026

Production уже містив код посилань, але в базі бракувало
`get_source_sync_state(uuid)` та
`register_drive_screenshot_reference(uuid,bigint,jsonb)`. Через це всі вісім
Drive jobs зупинилися з `PGRST202`, а нові файли не з'являлися на сайті.

Застосовано міграцію `20261111091818_repair_drive_reference_runtime.sql`,
яка додає лише ці дві службові RPC та оновлює кеш схеми PostgREST.
Вони доступні тільки `service_role`; доступ браузерів до реєстру продовжує
контролювати RLS. Історія відновлення та правила резервних копій не змінювалися.

Повторний запуск восьми Drive jobs завершився без помилок; зареєстровано
191 посилання, незавершених файлів у цих проходах не залишилося.
Сума розмірів `storage.objects` у bucket `screenshots` до та після:
1 563 140 614 байтів. Нових копій зображень у Storage не створено.
Реєстрацію на реальних записах також перевірено у транзакції з rollback:
збережено старий шлях і прив'язки, нових Storage objects не виникло.

Після виправлення потрібно оновити відкриту сторінку, щоб перечитати реєстр.
Додатковий лог адміна виявив два окремі випадки:

- `resolveSourceConnection` повертав віртуальний дозвіл адміна без `id`.
  Sync тепер спочатку перевіряє доступ service account до папки й зберігає
  справжнє підключення, а worker відхиляє відсутній ID до будь-яких RPC.
- Старі записи мали `source=upload`, `source_file_id=null` і шлях
  `screenshots/<owner>/<driveId>_<originalName>`. Міграція
  `20261111093210_preserve_legacy_drive_paths.sql` дозволяє прийняти такий
  точний шлях під час перевіреної індексації Drive. Зберігаються ID запису,
  шлях і прив'язки; запис отримує Drive ID і тип джерела. Чужі профілі та
  видалені файли не підбираються за одним лише ім'ям.

Це додаткове виправлення потребує деплою API. Build gate тепер перевіряє
обидві службові Drive RPC, використовуючи коректні набори аргументів без
права виконання для анонімного клієнта.

## Раніше створені копії

Зміна способу перегляду не видаляє попередні файли зі Storage. Перед очищенням
`scripts/verify-drive-originals.mjs` має звірити власника, дозволену папку,
розмір і SHA-256 оригіналу. Тільки після погодження конкретного перевіреного
списку можна видаляти відповідні копії через Storage API. Файли з непідтвердженим
оригіналом залишаються. Скрипт перевірки сам нічого не видаляє.
