## Логи та залишкові обмеження

- У доступних історичних Vercel групах були PGRST205 для відсутньої `integration_connections`, SOURCE_CONNECTION_REQUIRED і DEP0169. Таблиця зараз наявна; реальні перевірки з тестовими підключеннями успішні. Порожні або неавторизовані підключення не слід обходити відключенням перевірок доступу.
- У браузері відтворено мережеві помилки й `42501`; причини та виправлення наведені вище. Очікувані помилки під час навмисного offline не означають production 5xx.
- У виконаних RPC-сценаріях не було statement timeout, PGRST або невалідного API key. Повний історичний журнал Postgres недоступний у використаних інструментах; обмеження retention Vercel також не дозволяє стверджувати, що знайдено **всі** історичні 4xx/5xx.
- Тестова папка містить лише невелику кількість файлів: багатосторінкове читання Drive перевірене кодом/тестами, але не навантажувальним live-прогоном тисяч реальних файлів.
- Для власного робочого Google-акаунта треба підключити потрібні джерела в UI. Підключення аудиту належать лише синтетичному користувачеві й не налаштовують чужі акаунти.
- Потрібно розгорнути останні зміни клієнта та повторити короткий production smoke test. Для повного історичного аудиту помилок потрібен доступ до Postgres logs і довшого журналу Vercel.

## Доповнення 23 вересня: RPC 500 на великих settings

У production відтворено граничне навантаження: найбільший settings-документ займає приблизно 2,29 МБ, а 62 його історичні ревізії — приблизно 141 МБ. Попередній `pull_data_changes` спочатку матеріалізував усі повні JSON, а вже потім залишав останню ревізію. `pg_stat_statements` показав піки 7,62 с для pull і 6,77 с для apply при стандартному timeout authenticated 8 с; конкурентні вкладки додатково серіалізували навіть read-only pull ексклюзивним advisory lock.

Міграція `20260923042623_optimize_data_sync_large_json.sql` розгорнута в Supabase. Вона вибирає курсори до завантаження великих JSON, повертає одну останню settings-ревізію, використовує shared lock для паралельних pull і задає 30 с statement timeout / 20 с lock timeout для двох RPC. Історичні чи користувацькі дані не змінено й не видалено.

Після розгортання pull найбільшого профілю виконався за 295 мс і повернув рівно одну settings-ревізію. REST/JWT smoke test: apply 89 мс, duplicate 72 мс, pull 70 мс; вісім одночасних pull завершилися HTTP 200 за 75–336 мс. Повний набір: 336/336 тестів, статичний аудит без blocking issues.

Після повторного HTTP 500 розмір відповіді перевірено окремо від часу SQL: найбільший cursor-page мав майже 3 МБ, з яких 1,94 МБ займав `cumulativeSheetRows`. Міграція `20260923043823_bound_sync_pull_response.sql` обмежує серверну сторінку 25 курсорами та не повторює велику settings-ревізію на проміжних сторінках. Найбільша відповідь зменшилася до 2,31 МБ, решта — до 123 КБ; 11 сторінок пройшли за 0,6–162 мс без пропуску cursor. Дані settings не змінено.
