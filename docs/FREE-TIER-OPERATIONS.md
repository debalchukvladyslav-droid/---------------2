# Робота в межах безкоштовних квот

## Узгоджене рішення

29 жовтня 2026 власник обрав:

- Файли, імпортовані з Google Drive, залишаються в Drive. Supabase зберігає їхній реєстр і посилання.
- Для кожного користувача в базі залишаються три останні точки відновлення. Старші копії переносяться у приватний зашифрований архів Drive.
- Існуючі копії скріншотів у Supabase видаляються лише після перевірки оригіналів та погодження конкретного списку.

Доступність таких скріншотів залежить від збереження файлів і дозволів у вихідній папці Drive.
Ручні завантаження скріншотів та аватарів залишаються в Supabase Storage.

## Причини росту

Перевірка живих каталогів до призупинення проєкту виявила:

- 35 327 версій великих налаштувань, приблизно 1140 MB даних історії.
  У вибірці для більшості ключів понад 90% послідовних версій однакові.
- 62 371 запис історії `integration_connections`, приблизно 132 MB: переважно службові оновлення синхронізації.
- 806 точок відновлення, зокрема 630 щоденних. Inline snapshot займали приблизно 373 MB.
- 1563 MB файлів у `screenshots`, із них близько 1281 MB — копії Drive.
- 884 MB файлів у `journal-backups`.
- AI cron викликав Vercel кожні дві хвилини навіть без активних задач.
- Резервування щодня передавало історію і snapshot повторно; шлях кешу Storage не враховував абсолютний шлях усередині restic snapshot.

У Vercel надані власником 4 год 45 хв Active CPU перевищують включені 4 години.
Квоти: [Vercel](https://vercel.com/docs/functions/usage-and-pricing),
[Supabase](https://supabase.com/docs/guides/platform/billing-on-supabase).
Вже витрачений трафік і CPU не віднімаються після оптимізації.

## Обмеження в коді

| Ділянка | Поведінка |
| --- | --- |
| Storage | Глобальне резервування місця перед видачею upload token, Excel-експортом і записом ринкового кешу; поріг 900 000 000 байтів враховує паралельні завантаження та збільшення існуючих об'єктів |
| База | Записи журналу, угод, налаштувань і реєстру скріншотів, які збільшують дані, зупиняються після 475 000 000 байтів фізичного розміру, включно зі старими прямими шляхами запису; черга правок залишається на пристрої |
| Ринковий кеш | Додаткові записи припиняються при 430 MB бази або 80 MB сумарного кешу; наявні дані залишаються доступними для читання |
| Копії | Автоматичні snapshot не дублюють незмінений cursor; поріг 450 000 000 байтів; більше трьох копій не створюється без перевіреного архіву попередніх |
| Налаштування | Однакові значення не збільшують version і не створюють історію або Realtime подію |
| Google-підключення | Heartbeat зберігається в поточному стані, без повної копії конфігурації в історії |
| Sheets | Незмінені дані разом з незміненим мапінгом пропускають повторне читання журналу |
| Drive | Індексування метаданих без копіювання байтів; тихий клієнтський запуск не частіше одного разу на п'ять хвилин |
| Незмінений Drive | Порівняння стабільної версії папки та epoch до читання реєстру Supabase; незмінена папка не спричиняє скачування тисяч рядків; незавершений прохід не позначається завершеним |
| Перегляд | JWT та RLS перевіряють доступ до реєстру; сервер перевіряє папку Drive; приватний кеш на пристрої |
| AI cron | HTTP-пробудження лише за наявності активної задачі; важкі модулі завантажуються тільки для відповідної задачі |
| Vercel | Публічний конфіг кешується CDN на 5 хвилин; прихована сторінка не опитує рев'ю та індикатор ринку; помилки server-time мають 5-хвилинну паузу |
| Зовнішні копії | Storage: не більше 25 MB нових файлів за один запуск; при втраті кешу процес зупиняється до скачування. Повний SQL dump: попередня перевірка логічного обсягу до 20 MB; історія і старі точки архівуються окремо |
| 402 / 507 | Автоматичний sync відкладається на 30 хвилин; ручна спроба доступна; правки не видаляються і не переводяться в постійно заблокований стан |

Ці пороги обмежують основні потоки застосунку, але не обмежують весь обліковий запис провайдера:
ручні SQL-запити, сторонні клієнти, інші проєкти організації та необмежений зовнішній трафік враховуються окремо.
Перевірка фізичного розміру виконується перед записом, тому це запобіжний поріг із запасом,
а не транзакційна гарантія точного розміру після всіх індексів, історії, блоату та паралельних операцій.

## Порядок застосування

На момент останньої перевірки Supabase повертав `INACTIVE`, SQL був недоступний.
Зміни підготовлені локально; production міграції, архівування, очищення та deployment ще не виконувалися.

1. Після зняття обмежень підтримкою відновити запуск Supabase: власник уже дозволив відновлення без зміни тарифу.
2. Застосувати нові міграції в порядку:
   `20261029150057_reduce_redundant_sync_writes.sql`,
   `20261029150718_drive_references_and_archived_backups.sql`,
   `20261029152736_reserve_free_storage_capacity.sql`,
   `20261029181000_bound_derived_market_caches.sql`.
3. Перевірити сервісні RPC, звичайні права доступу та advisors. Розгорнути відповідний frontend/API та Edge Function `market-best-exits` зі спільним `storage_budget.js`.
4. Запустити `node scripts/archive-recovery.mjs` для плану. Для зовнішнього архівування потрібні налаштовані `SUPABASE_URL`,
   `SUPABASE_SERVICE_ROLE_KEY`, `RESTIC_PASSWORD`, Supabase CLI та rclone.
   На локальному Windows `RCLONE_CONFIG` має посилатися на приватний `.recovery/rclone.conf`.
5. `node scripts/archive-recovery.mjs --archive` копіює історію і точки відновлення,
   шифрує AES-256-GCM зі scrypt та gzip, читає кожен записаний архів із Drive назад і перевіряє SHA-256.
   `--prune` додатково перевіряє всі задіяні архіви, прибирає лише архівовані повтори/heartbeat і записи старші за попередній 30-денний строк,
   залишає три останні точки та видаляє їхні зайві Storage-файли через Storage API.
   Незавершене архівування або відповідь 402 залишають неперевірені дані на місці.
6. Запустити `node scripts/verify-drive-originals.mjs`. Це лише перевірка:
   власник, дозволена папка, розмір і SHA-256 мають збігатися. Результат —
   `.recovery/free-tier-archive/drive-retirement-plan.json`. Файли без надійної контрольної суми залишаються.
7. Показати власнику фактичну кількість і обсяг перевірених копій. Після погодження перевести відповідні записи на Drive та видалити лише перевірені байти через Storage API.
8. Після очищення погодити короткий період блокування двох таблиць для `VACUUM FULL`,
   описаного в [free_tier_cleanup.sql](../database/free_tier_cleanup.sql), і перевірити фізичний розмір бази знову.
9. Перевірити вхід, звичайне і відкладене збереження, скріншоти з Drive, ручне завантаження та відновлення останньої копії.

Саме видалення рядків не зменшує фізичний розмір бази відразу. Накопичений egress не скидається очищенням:
за [правилами Supabase](https://supabase.com/docs/guides/platform/manage-your-usage/egress) його квота поновлюється в наступному розрахунковому періоді.

## Перевірка після запуску

До зняття блокування неможливо підтвердити новий фактичний розмір або місячний прогноз.
Після застосування змін виконати [free_tier_usage.sql](../database/free_tier_usage.sql),
записати показники Usage обох провайдерів і повторити вимірювання через 24 та 48 годин.
Трафік і CPU брати за фактичний розрахунковий період, включно з іншими проєктами команди/організації.

Операційні цілі з запасом: база до 350 MB, Storage до 700 MB, прогноз Supabase egress до 3,5 GB/період,
Vercel Active CPU до 3 год/період, Provisioned Memory до 270 GB-год/період.
Прогнозувати окремо фонове споживання за добу й споживання за активний день користувачів;
перший експорт накопиченої історії враховувати окремо від звичайного режиму.
Короткий локальний тест не підтверджує місячне використання Vercel CPU.

Ліміт Storage backup 25 MB/запуск дає до 775 MB нових файлів за 31 щоденний запуск,
без урахування запитів інвентаризації. 20 MB SQL — логічний обсяг рядків перед dump,
а не гарантований розмір мережевого трафіку: є протокол, екранування та каталог.
Окреме архівування нової історії, звичайні API-запити, Realtime та перегляд ручних завантажень
також споживають egress. Загального ліміту мережевого трафіку цими перевірками не встановлено.
Скріншоти Drive тепер проходять через приватний проксі Vercel і кеш пристрою;
цей трафік треба включати у Fast Data Transfer та Fast Origin Transfer Vercel.

Якщо прогноз перевищує цілі або звичайна копія впирається в бюджет, спочатку показати власнику
конкретне джерело, обсяг і варіанти скорочення. Не підвищувати тариф, не збільшувати автоматично
бюджети й не видаляти користувацькі дані. Успішна перевірка архіву не підміняє успішну повну копію.

## Зовнішній архів та відновлення

Файли `.tjarchive` знаходяться в `TraderJournalBackups/free-tier-archive` приватного Drive.
Потрібен той самий `RESTIC_PASSWORD`; ключ не потрапляє у файли репозиторію або журнал виводу.
Окремий state містить checkpoint, а таблиці `restore_point_archives` і `history_archives` — перевірені квитанції.
У квитанціях історії збережені точні ID рядків, тому незавершена пізня транзакція не потрапить під очищення лише через діапазон ID.

Відновлення окремої точки в файл для стандартного імпорту:

```powershell
node scripts/archive-recovery.mjs --extract PATH_TO_ARCHIVE --point RESTORE_POINT_UUID
```

Результат `.tjbackup.json` містить snapshot і перевіряється звичайним preview/import перед відновленням.
Старі snapshot, створені до перенесення скріншотів, можуть вимагати відновлення згаданих у їхньому маніфесті файлів.
Їх не можна оголошувати повністю відновлюваними без окремої перевірки.
